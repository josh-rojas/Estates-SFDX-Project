# D2 Diagramming Prompt & Styling Guide for Salesforce Systems Architecture and Data Models

**Last Updated:** November 14, 2025  
**Primary Audience:** AI agents and automation frameworks that generate D2 diagrams for the Estates Salesforce program  
**Default Layout Engine:** `tala` (fall back to `elk` or `dagre` if unavailable)

---

## 1. Executive Summary

This guide packages everything an AI agent needs to produce Salesforce-compliant D2 diagrams for architecture, process, and data-model documentation. It fuses Salesforce's official diagramming standards with the repo's existing conventions so autogenerated diagrams are:

- **Production ready** with consistent styling, typography, and Salesforce branding.
- **Accessible** under WCAG 2.1 (4.5:1 contrast, 50-point color spacing, no color-only meaning).
- **Automation friendly** thanks to D2-as-code, scripted rendering (`scripts/render_d2.sh`), and Tala-first layout defaults.
- **Portable** so this folder can become its own repository later without rework.

Use this guide whenever an AI agent needs to generate, extend, or validate D2 diagrams inside `docs/diagrams/d2/` (sources) and `docs/diagrams/svg/` (outputs).

> You are a specialized diagramming agent that writes complete D2 (Declarative Diagramming) code for Salesforce systems. Your mission is to create Salesforce-compliant architecture, integration, data-model, and process diagrams that honor official Salesforce diagramming standards, WCAG 2.1 accessibility, and the Estates project conventions. Use the Tala layout engine by default (`layout-engine: tala`); gracefully fall back to `elk` or `dagre` if Tala is unavailable.
>
> **Primary objectives:**
> 1. Generate production-ready D2 code that can be rendered through `scripts/render_d2.sh` without manual edits.
> 2. Guarantee accessibility (4.5:1 contrast minimum, Salesforce 50-point color rule, descriptive labels).

> - Capability Maps (business drivers, functionality groupings, property mixes).
> - Process Flows / Interaction Diagrams (sequence/timeline, numbered steps, `sequence_diagram` when appropriate).
>
> Before returning D2 output: run through the validation checklist in this guide, ensure Tala defaults are applied, and document rendering instructions for humans.

## 4. Styling & Components Reference

### 4.1 Color System (Salesforce Vibrant Palette)

```d2
vars: {
  palette: {
    sf-blue-10: "#F3F9FF"
    sf-blue-30: "#AACBFF"
    sf-blue-50: "#1B96FF"
    sf-blue-70: "#0176D3"
    sf-blue-90: "#001F3D"
    sf-green-50: "#3BA755"
    sf-orange-50: "#FE9339"
    sf-red-50: "#EA001E"
    sf-purple-50: "#9050E9"
    sf-gray-10: "#F3F2F2"
    sf-gray-30: "#DDDBDA"
    sf-gray-50: "#969492"
    sf-gray-70: "#514F4D"
    sf-gray-90: "#201F1E"
  }
}
```

- **Contrast rule:** Ensure text color differs by ≥4.5:1 from fill color (e.g., `sf-blue-70` background pairs with `sf-blue-10` text).
- **50-point rule:** Background and foreground values must differ by at least 50 (70 background pairs with ≤20 text).

### 4.2 Header Block (Mandatory)

```d2
header: {
  shape: rectangle
  style: {
    fill: transparent
    stroke: transparent
  }

  title: {
    shape: text
    label: "Diagram Title"
    style: {
      font-size: 24
      bold: true
      font-color: palette.sf-blue-90
    }
  }

  description: {
    shape: text
    label: "Scope, purpose, and context"
    style: {
      font-size: 12
      font-color: palette.sf-gray-70
    }
  }

  key: |md
    **Legend**
    🔵 Salesforce Core
    ⚪ Platform Objects
    🟢 External Systems
  |
}
```

Requirements:
- Consume ≥10% height and 100% width.
- Include clear title and descriptive sentence (or two) explaining scope.
- Optional logo, company name, and legend.

### 4.3 Card Templates

```d2
ComponentName: {
  shape: rectangle
  label: "Display Name"
  attributes: |md
    • Attribute 1
    • Attribute 2
    • Attribute 3
  |
  footer: "API Name / Notes"
  style: {
    fill: palette.sf-blue-10
    stroke: palette.sf-blue-70
    font-size: 12
  }
}
```

Variations:
- **Collapsed:** just label.
- **Detailed:** label + bullet attributes.
- **Detailed w/ footer:** include API names or system IDs.
- **Icon support:** `icon: <SLDS URL>` for brand consistency.

### 4.4 Entity Formatting

| Type | Fill | Stroke | Notes |
| --- | --- | --- | --- |
| Cloud Entity (primary focus) | `sf-blue-70` | same or darker (`sf-blue-90`) | White text |
| Related Platform Entity | `#FFFFFF` | `sf-gray-90` | Neutral style |
| Extended Related Entity | `sf-gray-10` | `sf-gray-90` | Optional dotted pattern |
| External Entity | transparent | `sf-gray-70` dashed | Use `shape: cloud` if virtual |
| Record Type Entity | follow base entity but `stroke-dash: 3` | indicates RT |
| Conceptual Entity | `stroke-dash: 1` | dotted outline |

### 4.5 Data Model / ERD

- Always use `shape: sql_table`.
- Include PK/FK/UNQ constraints.
- Show relationships with labels that capture cardinality and optionality.

```d2
Account: {
  shape: sql_table
  Id: string {constraint: primary_key}
  Name: string
  ParentId: string {constraint: foreign_key}
  OwnerId: string {constraint: foreign_key}
  style: {
    fill: palette.sf-blue-70
    stroke: "#014486"
    font-color: "#FFFFFF"
  }
}

Contact: {
  shape: sql_table
  Id: string {constraint: primary_key}
  AccountId: string {constraint: foreign_key}
  Email: string {constraint: unique}
  style: {
    fill: "#FFFFFF"
    stroke: palette.sf-gray-90
  }
}

Account.Id -> Contact.AccountId: {
  label: "Primary Account 1:N"
  style: {
    stroke: palette.sf-blue-70
    stroke-width: 2
  }
}
```

### 4.6 Connector Standards

| Relationship | Style |
| --- | --- |
| Parent-Child (Master-Detail) | solid `sf-blue-70`, width 2, diamond at source |
| Lookup | solid `sf-gray-70`, width 2 |
| Integration/API | dashed `sf-green-50`, include protocol label |
| Process Step | solid `sf-blue-70`, width 2, numbered label |
| Optional link | dashed stroke |

Use elbow/orthogonal routing (Tala does this automatically). Add labels with clear verbs ("Publishes Platform Event", "REST API", etc.).

### 4.7 Cardinality & Optionality

- `label: "1:N (Required)"` for required relationships.
- `style.stroke-dash: 3` for optional edges.
- Circles and bars (○, ||) can be embedded in labels for clarity.

### 4.8 Containers & Grouping

```d2
SalesforceOrg: {
  label: "Production Org"
  style: {
    fill: palette.sf-blue-10
    stroke: palette.sf-blue-70
    stroke-width: 2
  }

  SalesCloud: {
    label: "Sales Cloud"
    style.fill: "#E7F3FF"
  }
}
```

Group by cloud, service, or architecture layer. Keep container labels short.

### 4.9 Layout Configuration (Tala-first)

```d2
vars: {
  d2-config: {
    layout-engine: tala
    theme-id: 200
    pad: 20
    sketch: false
  }
}

direction: right
```

- **Default direction:** `right` for readability (left-to-right data flow).
- **Fallback:** switch `layout-engine` to `elk` or `dagre` if Tala is unavailable; call this out in diagram notes.

### 4.10 Icons & Shapes

- Use SLDS icons when referencing Salesforce clouds (`https://www.lightningdesignsystem.com/assets/icons/standard/service_cloud.svg`).
- Built-in shapes: `person`, `cloud`, `cylinder`, `stored_data`, `page`.
- For multiple instances: `shape.multiple: true`.

### 4.11 Typography

| Use Case | Size | Notes |
| --- | --- | --- |
| Title | 24 | Bold |
| Section headings | 18 | Bold optional |
| Body text (cards, tables) | 12 | Default |
| Captions/notes | 10 | Use for footers |

### 4.12 Accessibility Checklist

- Contrast ratio ≥ 4.5:1.
- 50-point Salesforce color gap.
- Provide alternative text via descriptive labels.
- Never rely solely on color; include icons/patterns/labels.
- Use PDF exports when screen-reader friendly output is needed (`d2 diagram.d2 diagram.pdf`).

## 6. D2 Generation Workflow (For Agents)

1. **Analyze requirements**
   - Identify diagram type, audience, scope, entities/components, relationships.
   - Confirm needed annotations (SLA notes, system modes, etc.).
2. **Structure D2 skeleton**
   - Declare `vars` with `layout-engine: tala`, `theme-id`, padding, sketch flag.
   - Set `direction` (usually `right`).
   - Build header block (title, description, optional key/legend).
3. **Define entities/components**
   - Use correct shapes (`sql_table`, `rectangle`, `person`, etc.) and styling class.
   - Add attributes, footers, icons as required.
4. **Connect elements**
   - Apply connector standards (Section 4.6) and cardinality labels.
   - Number process steps sequentially.
5. **Apply palettes & typography**
   - Reference Section 4.1 and 4.11 for colors and sizes.
6. **Optimize layout**
   - Use containers to group layers/clouds.
   - Break large diagrams into modules if Tala struggles; optionally switch to `elk`.
7. **Validate**
   - Run through Section 8 checklists (syntax, Salesforce standards, accessibility, readability).
8. **Document rendering instructions**
   - Provide commands for `d2` CLI or `scripts/render_d2.sh` (see Section 7).

## 7. Rendering Instructions (Human + Agent)

### 7.1 Scripted (Tala default)

```bash
D2_LAYOUT=tala ./scripts/render_d2.sh
```

- Script adds `$HOME/.local/bin` to `PATH`, enforces `--theme 200 --pad 20 --sketch=false`, and iterates through `docs/diagrams/d2/*.d2`.
- If Tala is unavailable, rerun with `D2_LAYOUT=elk` (default) or `dagre`.

### 7.2 Manual / Single Diagram

```bash
export PATH="$HOME/.local/bin:$PATH"

d2 --layout tala --theme 200 --pad 20 --sketch=false \
  docs/diagrams/d2/diagram.d2 \
  docs/diagrams/svg/diagram.svg
```

### 7.3 Output Variants

```bash
# PNG
d2 diagram.d2 diagram.png

# PDF (screen-reader friendly)
d2 diagram.d2 diagram.pdf
```

Document any non-standard flags (e.g., `--layout elk`) inside the guide when sharing with others.

## 8. Validation & Quality Checklists

### 8.1 Technical
- D2 syntax passes (`d2 --dry-run file.d2`).
- `vars.d2-config.layout-engine` set to `tala` (or fallback noted).
- Direction set explicitly if non-default.
- All connectors reference existing nodes.
- No orphaned nodes or empty containers.

### 8.2 Salesforce Standards
- Header present with title + description, optional legend.
- Entities use proper shape/color per type.
- Cardinality and optionality shown where relevant.
- API names or technical details captured in footers or notes.
- Containers/groupings reflect Salesforce architecture layers.

### 8.3 Accessibility
- Color contrast verified (use e.g., `contrast-ratio.com`).
- 50-point rule satisfied for text vs. background.
- Descriptive labels for each node; include alt-text style descriptions where helpful.
- Legend clarifies icons, connector colors, dashed semantics.
- No reliance on color alone to convey meaning.

### 8.4 Readability
- Logical left-to-right or top-to-bottom flow.
- Lines remain straight; minimal crossings.
- Containers keep related elements together.
- Numbered steps for sequences; timeline obvious.
- Notes call out constraints (SYSTEM_MODE, inactive flows, etc.).

## 10. Advanced Patterns Library

### 10.1 Subtypes / Record Types

```d2
Account: {
  shape: sql_table
  Id: string {constraint: primary_key}
  Name: string
  RecordTypeId: string

  BusinessAccount: {
    shape: rectangle
    label: "Business Account (Record Type)"
    style: {
      stroke-dash: 3
      fill: palette.sf-blue-10
    }
  }

  PersonAccount: {
    shape: rectangle
    label: "Person Account (Record Type)"
    style: {
      stroke-dash: 3
      fill: palette.sf-blue-10
    }
  }
}
```

### 10.2 Mutually Exclusive Relationships

```d2
Contact: {
  shape: sql_table
  Id: string {constraint: primary_key}
  AccountId: string {constraint: foreign_key}
  ReportsToId: string {constraint: foreign_key}
}

Contact.AccountId -> Account.Id: {
  label: "Related to Account OR"
}

Contact.ReportsToId -> Contact.Id: {
  label: "Reports to Contact (recursive)"
  style.stroke-dash: 5
}

mutualExclusiveNote: |md
  **Note:** A Contact must relate to either an Account or another Contact, but not both simultaneously.
|
```

### 10.3 Multi-Org Architecture

```d2
production: {
  label: "Production Org"
  style.fill: palette.sf-blue-10
  style.stroke: palette.sf-blue-70
  style.stroke-width: 3
}

sandbox: {
  label: "Sandbox Org"
  style.fill: "#FFF9E6"
  style.stroke: palette.sf-orange-50
  style.stroke-width: 3
}

production -> sandbox: {
  label: "Change Set Deployment"
  style.stroke: palette.sf-gray-70
  style.stroke-width: 2
}
```

### 10.4 Junction Object Pattern

```d2
OpportunityContactRole: {
  shape: sql_table
  Id: string {constraint: primary_key}
  OpportunityId: string {constraint: foreign_key}
  ContactId: string {constraint: foreign_key}
  Role: picklist
  IsPrimary: boolean
  style.fill: palette.sf-gray-10
  style.stroke: palette.sf-gray-90
}

Opportunity.Id -> OpportunityContactRole.OpportunityId: { label: "1:N" }
Contact.Id -> OpportunityContactRole.ContactId: { label: "1:N" }
```

### 10.5 Numbered Process Steps

```d2
step1: { label: "1. User Submits Form" }
step2: { label: "2. Validation" }
step3: { label: "3. Trigger Fires" }
step4: { label: "4. Records Saved" }

step1 -> step2 -> step3 -> step4: {
  style.stroke: palette.sf-blue-70
  style.stroke-width: 2
}
```

## 11. Output & Customization Notes

When delivering D2 output:

1. **Provide complete code** with all vars, header, nodes, and connectors—ready for `d2` CLI.
2. **State rendering command** (Tala default), e.g. `D2_LAYOUT=tala ./scripts/render_d2.sh`.
3. **Explain customization hooks:**
   - How to adjust colors (e.g., swap `palette.sf-blue-70` for a brand-specific hex).
   - How to add/remove entities or containers.
   - Layout alternatives (switch to `elk` for hierarchical ERDs, `dagre` for simple flows).
4. **Describe the diagram** in natural language (what it shows, assumptions, key decisions).
5. **Suggest alternatives** if there are other viable views (e.g., separate diagram per pathway).
